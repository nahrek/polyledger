# PolyLedger

*Read this in [English](README.md).*

Индексатор данных Polymarket: тянет метаданные рынков из CLOB API, стримит все
исполненные сделки прямо из блокчейна Polygon и складывает всё в один файл
DuckDB, по которому можно сразу писать SQL.

Главное отличие от похожих проектов — процесс можно прервать в любой момент.
Строки и указатель на последний обработанный блок пишутся одной транзакцией,
поэтому после `Ctrl+C`, падения сети или ребута следующий запуск продолжит
ровно с того места и ничего не задублирует.

```bash
polyledger sync          # рынки -> сделки -> добор пропусков -> джойн
polyledger query "SELECT question, sum(usd_size) FROM trades GROUP BY 1 ORDER BY 2 DESC LIMIT 10"
```

---

## Что внутри

Три стадии, каждая запускается отдельно или все разом через `sync`:

| Стадия | Откуда | Куда |
|---|---|---|
| `markets` | CLOB API `/markets` (+ Gamma для пропусков) | таблицы `markets`, `tokens` |
| `chain` | логи `OrderFilled` из Polygon через Envio HyperSync | таблица `order_fills` |
| `trades` | SQL-джойн первых двух | таблица `trades_mat` |

Представление `trades` существует всегда и всегда актуально — стадия `trades`
нужна только чтобы материализовать джойн и не пересчитывать его на каждом
запросе.

## Установка

```bash
git clone <repo> && cd polyledger
python -m venv .venv && source .venv/bin/activate
pip install -e .
```

Нужен Python 3.11+.

Дальше — токен HyperSync. Он обязателен с ноября 2025, бесплатного тарифа
хватает: регистрация на [envio.dev](https://envio.dev), потом

```bash
cp .env.example .env
# впишите HYPERSYNC_BEARER_TOKEN=...
export $(grep -v '^#' .env | xargs)
```

CLOB и Gamma публичные, ключи для них не нужны.

## Первый запуск

```bash
polyledger sync
```

Первый бэкфилл долгий: на бесплатном тарифе HyperSync это от нескольких часов
до пары суток в зависимости от того, сколько истории вы качаете. Прерывать
можно свободно. Все последующие запуски — инкрементальные и занимают секунды.

Если хочется сначала просто убедиться, что всё живо, возьмите кусок:

```bash
polyledger markets                    # только метаданные, пара минут
polyledger chain --max-blocks 200000  # ~5 дней истории Polygon
polyledger stats
```

`stats` покажет, что реально лежит в базе:

```
  markets          14231
  tokens           28455
  fills            1204773
  unmatched_fills  392
  first_block      75014820
  last_block       75214820
  first_time       2026-05-14 08:11:23
  last_time        2026-05-19 03:44:02
  checkpoints:
    order_filled:v2: block 75214820, 1204773 rows, updated 2026-09-02 15:11:23
```

## Команды

```
polyledger markets [--backfill]     метаданные рынков из CLOB
polyledger chain   [--contracts v2|v1|all] [--from-block N] [--to-block N] [--max-blocks N]
polyledger trades  [--drop-unmatched]
polyledger sync    [--max-blocks N] [--skip-markets]
polyledger stats
polyledger export  [--out DIR]      выгрузка всех таблиц в Parquet
polyledger query   "SELECT ..."     разовый SQL
```

Глобальные флаги: `--db PATH` (другой файл базы), `-v` (подробный лог).

## Данные

### `trades` — то, ради чего всё затевалось

| Поле | Что это |
|---|---|
| `block_time`, `block_number` | время и высота блока (UTC) |
| `question`, `market_slug`, `outcome` | человекочитаемый контекст |
| `token_id`, `condition_id` | идентификаторы рынка и исхода |
| `maker`, `taker` | адреса сторон |
| `maker_side`, `taker_side` | `BUY` / `SELL`, обе стороны явно |
| `price` | цена исполнения, 0…1 |
| `shares` | количество долей исхода |
| `usd_size` | объём в долларах |
| `fee` | комиссия |
| `unmatched_market` | `true`, если метаданные рынка не нашлись |

`price`, `shares` и `usd_size` не лежат в блокчейне — они выводятся из
`makerAmountFilled` / `takerAmountFilled` в зависимости от стороны мейкера.
Если мейкер покупал, его сумма — это доллары, а сумма тейкера — доли; если
продавал, наоборот. Обе величины в базовых единицах с 6 знаками, как pUSD.

`maker_side` — это сторона мейкера, `taker_side` всегда противоположна. Многие
датасеты схлопывают это в одно поле `side` и потом невозможно понять, чью
сторону имели в виду. Здесь обе.

### Остальные таблицы

* `markets` — одна строка на рынок (`condition_id`), с вопросом, слагом,
  флагами `active`/`closed`/`neg_risk`, тиком и комиссиями.
* `tokens` — одна строка на исход (`token_id`). Это ключ джойна к сделкам.
* `order_fills` — сырые декодированные логи, без интерпретации. Если вы не
  согласны с тем, как я считаю цену, стройте свой джойн отсюда.
* `checkpoints` — по строке на поток индексации.

Готовые запросы (дневные объёмы, OHLC по свечам, VWAP, позиции адреса,
топ трейдеров) лежат в [`examples/queries.sql`](examples/queries.sql).

Базу можно открыть чем угодно, что умеет DuckDB:

```python
import duckdb
con = duckdb.connect("data/polyledger.duckdb", read_only=True)
df = con.sql("SELECT * FROM trades WHERE token_id = '1001'").df()
```

Или выгрузить в Parquet (`polyledger export`) и читать из pandas/polars/Spark.

## Какие контракты индексируются

По умолчанию — V2, живущие с миграции апреля 2026:

| Контракт | Адрес |
|---|---|
| CTF Exchange V2 | `0xE111180000d2663C0091e4f400237545B87B996B` |
| NegRisk CTF Exchange V2 | `0xe2222d279d744050d28e00520010520000310F59` |
| NegRisk CTF Exchange V2 (b) | `0xe2222d002000ba0053cef3375333610f64600036` |

`--contracts v1` переключит на замороженные V1 (`0x4bFb41d5…`,
`0xC5d563A3…`), `--contracts all` соберёт всё сразу. У V1 и V2 разные схемы
события `OrderFilled`, декодер понимает обе:

```
V2: OrderFilled(bytes32 orderHash, address maker, address taker, uint8 side,
                uint256 tokenId, uint256 makerAmountFilled,
                uint256 takerAmountFilled, uint256 fee,
                bytes32 builder, bytes32 metadata)

V1: OrderFilled(bytes32 orderHash, address maker, address taker,
                uint256 makerAssetId, uint256 takerAssetId,
                uint256 makerAmountFilled, uint256 takerAmountFilled, uint256 fee)
```

В V2 сторона сделки лежит в событии явным полем. В V1 её приходится выводить:
нулевой `assetId` — это залог, и та нога, которая нулевая, показывает
направление мейкера. Обмены «токен на токен» в V1 (комплементарные исходы)
пропускаются — в них нет долларовой ноги, а значит нет и цены.

У каждого потока свой чекпоинт, так что `--contracts all` не сломает курсор,
набитый предыдущими запусками с `v2`.

С какого блока начинать, задавать не нужно. Если чекпоинта нет и
`POLYLEDGER_FROM_BLOCK` не выставлен, PolyLedger сам находит первый блок с
подходящим логом — HyperSync проматывает пустые диапазоны на своей стороне, так
что это занимает несколько запросов, а не скан всей цепи.

## Настройки

Всё через переменные окружения или `.env`:

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `HYPERSYNC_BEARER_TOKEN` | — | токен Envio, обязателен |
| `POLYLEDGER_DB` | `data/polyledger.duckdb` | файл базы |
| `POLYLEDGER_CONTRACTS` | `v2` | `v2` / `v1` / `all` |
| `POLYLEDGER_FROM_BLOCK` | `0` | `0` — определить автоматически |
| `POLYLEDGER_REORG_BUFFER` | `64` | на сколько блоков отставать от головы цепи |
| `POLYLEDGER_FLUSH_EVERY` | `50000` | сколько сделок копить до сброса в базу |
| `POLYLEDGER_HTTP_RPS` | `8` | лимит запросов в секунду к CLOB и Gamma |
| `POLYLEDGER_HTTP_CONCURRENCY` | `8` | параллельные HTTP-запросы |
| `POLYLEDGER_HTTP_RETRIES` | `6` | попыток на запрос |

`REORG_BUFFER` — защита от реорганизаций: индексация останавливается за 64
блока до головы цепи, чтобы не записать сделку из блока, который потом
откатится.

## Почему сделано именно так

**DuckDB, а не CSV.** Дозапись в CSV на несколько гигабайт деградирует
бесконечно, а любое чтение — это парсинг всех байтов. DuckDB даёт колоночное
сжатие, типы, индексы и настоящий SQL-джойн вместо `pandas.merge`, который
требует держать оба датасета в памяти. При этом это по-прежнему один файл на
диске: ни сервера, ни демона.

**Идемпотентная запись.** У `order_fills` первичный ключ
`(transaction_hash, log_index)` и вставка через `ON CONFLICT DO NOTHING`.
Повторный прогон того же диапазона ничего не сломает и ничего не задублирует.
Дубликаты внутри одного батча тоже схлопываются.

**Атомарные чекпоинты.** Строки и новое значение курсора пишутся одной
транзакцией. Не бывает состояния «данные записались, а курсор нет» или
наоборот.

**Валидация схемы.** Всё, что приходит из API, проходит через pydantic-модели.
Когда Polymarket в следующий раз поменяет формат ответа (как в апреле 2026),
пайплайн упадёт с внятной ошибкой на первой же строке, а не запишет молча
шесть часов `NULL`-ов.

**Ретраи с джиттером и общий рейт-лимитер.** Многочасовой бэкфилл гарантированно
поймает 502 или таймаут. Экспоненциальный бэкофф с полным джиттером и уважением
к `Retry-After` вытаскивает такие случаи. Токен-бакет один на все REST-источники,
поэтому параллельный добор через Gamma не может выйти за общий бюджет.

**Пропуски видны, а не замалчиваются.** Часть `token_id` из старых сделок нет в
листинге CLOB. Такие строки помечаются `unmatched_market = true`, попадают в
`stats` и добираются через Gamma по `--backfill`. Данные при этом не теряются:
сделка остаётся в базе, просто без человекочитаемого контекста.

## Тесты

```bash
pip install -e ".[dev]"
pytest
```

41 тест, сети не требуют: декодирование обеих версий события на фикстурах,
идемпотентность и откат транзакций, арифметика цены и сторон, пагинация CLOB
(включая защиту от зацикленного курсора), батчинг Gamma, рейт-лимитер и
бэкофф. Отдельный тест пересчитывает `topic0` из текстовых сигнатур и сверяет
с захардкоженными хешами — если кто-то опечатается в константе, тест это
поймает.

## Ограничения

* Только Polymarket. Kalshi торгуется не в блокчейне, там нужен совсем другой
  сборщик; архитектура стадий это позволяет, но код пока не написан.
* Только исполненные сделки. Стакан, котировки и отменённые ордера в блокчейн
  не попадают — их можно собрать только с WebSocket CLOB в реальном времени.
* Реорганизации обрабатываются отставанием от головы цепи, а не откатом уже
  записанных блоков. Для исторического анализа этого достаточно; для торговли
  в реальном времени — нет.
* Гонорары мейкера/тейкера берутся из поля `fee` события, отдельные события
  `FeeCharged` не индексируются.
